title: A debugging method you can say out loud
source: v1
points:
  - 1. <b>State the symptom exactly:</b> what failed, how often, since which build, on which phones.
  - 2. <b>Reproduce</b> it and find the smallest setup that still fails.
  - 3. <b>Build a timeline:</b> align phone log, network log and test script log on one clock.
  - 4. <b>Find the last good message</b> and the first wrong or missing one.
  - 5. <b>Pick the layer:</b> if a message was sent but not received, go down. If it was received and rejected, go up.
  - "6. <b>Compare</b> with a passing run: different build, different phone, different config."
  - 7. <b>Make one hypothesis and test it</b> by changing one thing.
  - 8. <b>Classify:</b> phone, base station, core, configuration, RF setup, or the test itself.
  - 9. <b>Report:</b> evidence, root cause or best narrowing, and a regression test.
say: Symptom, reproduce, timeline, last good message, pick the layer, compare with a pass, test one hypothesis, report with evidence.
trap: Jumping to a guess before building the timeline is the most common mistake under interview pressure. Say 'first I would build the timeline'.
